## 回收系统（recycle）权限与审批架构设计咨询

结合前端项目 `/Users/zhangjingjie/Documents/code/recycle-app`（Taro 小程序，空墨盒/空硒鼓回收）的业务，
为 nestjs 微服务项目设计「订单 + 审批 + 细粒度权限」方案。

### 既有底座（可直接复用）
- `libs/common/src/gateway-routes.ts`：`business()/platform()` + `permissions` 数组，接口级静态权限（L1）
- `apps/gateway/src/auth/auth.service.ts`：`enforce()` 校验 permission，`admin` 自动放行

- 业务准入靠 `X-Biz-Code` + Redis 业务注册表（`biz.guard.ts` / `biz-access.ts`）

### 设计结论
提出四层权限模型：L1 接口准入（已有）/ L2 动作授权（缺，需新建）/ L3 数据范围（行级）/ L4 字段权限（列级）。
核心是「状态转移授权矩阵」：action × 角色 × 起始状态 → 目标状态 + 附加业务规则。

关键洞察：前端 `POST /orders/:id/actions/reject` 在 `INSPECTING` 是 B 端验收驳回，在 `EVALUATED` 是 C 端拒绝报价，
同一接口不同身份语义不同 —— 必须拆成两个 action（`reject_inspect` / `reject_offer`），不能靠前端传状态区分。

### 角色划分
客户 / 业务员（收货、退货）/ 验收员（评估报价、验收驳回）/ 审批员（协商定价决策）/ 财务（打款）/ 超管

## 第六轮：微信相关能力是否进 recycle 服务（分析结论，未动手）

### 边界判断
- **不该搬进 recycle**：微信登录 code2session（usercenter `loginByWechat`）、手机号解密（`/wechat/phone`）、
  小程序码（`/wechat/qrcode`）。recycle 只消费网关注入的 `_session`，重复实现会变成两套身份体系。
- **必须补到 recycle**（否则业务闭环不了）：
  A. 可信 openid —— 见下，安全洞
  B. 订阅消息 —— 状态变更要通知用户，recycle 是唯一知道状态变更的点；
     但 wechat 服务目前只有 code2session/qrcode/phone，**没有 subscribeMessage 能力**
  C. 商家转账 —— `transfer` 现在只把状态改成 paid，没有真打款

### 新发现的两个信任洞（与 price 同类）
1. `orders.service.ts:267` `ownerOpenid: optionalString(payload.openid) ?? null`
   —— openid 直接取客户端 body，可伪造。且 `AuthSession` 里**根本没有 openid 字段**，
   只有 `wechatAppId`。正确做法：usercenter 登录时把 openid 写进 session，recycle 从 `_session` 取。
2. `transfer` 的 `billNo` 也来自客户端（`payload.billNo`），同样不该采信。

### 解耦约束
recycle 不能直接引微信 SDK / 直连微信 API；应像 orders→approvals 一样走 MQTT 单向事件
（recycle 发「通知意图」，wechat 服务决定用订阅消息还是别的方式发），wechat 不认识 recycle。

### 建议优先级
A（马上补，安全洞） → B（wechat 服务加 subscribeMessage + 模板 ID 下发） → C（依赖微信支付商户号）

`wx.login() → code` → `POST /auth/wechat`（网关 → **usercenter**）→ usercenter 内部经 MQTT
调 wechat 服务 `code2session` 换 openid → 建/找账户 → 签发 JWT。
所以：换 code 的是 usercenter，wechat 服务只提供原语（code2session/phone/qrcode），
openid **不会下发给前端**，也不需要下发。
请求头：`X-Biz-Code: recycle`（必填）+ `Authorization: Bearer <token>`（登录后）。
`clientCode` 选填：业务下只有 1 个 wechat_mp 接入端时可省，多个则必须传。
前置：wechat 服务先登记小程序 appId/secret，usercenter 给 recycle 业务建 wechat_mp 接入端。

## 第八轮：回收接口的公开 / 需登录划分（重要网关机制）

### 发现的机制（很容易踩）
网关 `AuthService.enforce()`：
`allowJwt = auth?.includes('jwt') || auth?.includes('admin') || !!permissions?.length`
→ **路由只要声明了 `permissions`，就等价于强制登录**。想让接口公开，就不能挂 `permissions`。
而 `business` scope 本身**允许无会话**（`evaluateBizAccess` 里 session 为 null 时跳过
「会话不属于该业务」校验），只要求 `X-Biz-Code` 有效 + 业务 apis 清单含该路由。
所以「公开但仍受业务准入约束」= `business({...})` 且不写 permissions。

### 最终划分
- **公开**：`GET /recycle/health`、`GET /recycle/cartridges{,/types,/brands,/models}`
  （价目表，游客可看；仍需 X-Biz-Code，缺 400 / 非法业务 403）
- **登录 + 权限**：`POST /recycle/quotes`（quote.create，写型可刷，登录后才能按用户限流）、
  `GET /recycle/policy/transitions`、所有 orders*、所有 approvals*
