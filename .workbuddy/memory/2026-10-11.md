## 契约决策：接入端 code 的字段名 = clientCode（不用 appCode）
- 根因：网关 `buildProxyPayload` 会丢弃请求体/query 里的 `appCode`（有单测固化
  `expect(payload).not.toHaveProperty('appCode')`），只把 `X-App-Code` 头或 session.appId
  注入成 `_appCode`；而 `ClientsService.create` 读的是 `payload.appCode` → **POST /clients
  经网关从来没成功过**。
- 定案：输入字段改 `clientCode`（与 `/auth/login` 命名一致），网关约束不动；
  响应仍返回 `appCode`。已改 `rpc.ts` / `clients.service.ts`（create+update）/ admin wechat 页 / README，
  并新增 `apps/usercenter/test/apps/client-code.spec.ts`。
- **附带修掉的隐患**：`clientCodeOf` 原本有 `?? appId` 兜底，而网关会注入调用方 appId，
  导致「忘传 code」时静默用调用方 code 建出错误接入端（实测建出了 appCode=platform 的脏行，已删）。
  现在只认 `clientCode ?? appCode`，绝不回落 appId。

## 环境问题（重要）
- **磁盘只剩 ~200MB（99% 满）**：root 卷。Docker 数据 36G、`~/Library/Caches` 10G 是大头。
  曾导致 Docker 守护进程崩溃（PG/Redis/MQTT 全停，后端全退）、沙箱无法创建（`/dev/null`
  resource unavailable）。**清理前 shell 会时好时坏。**
- **沙箱下 `nest build` 不可用**：文件代理把「对已存在目录 mkdir」误判为非法操作
  （`EEXIST ... mkdir 'dist'` → `CODEBUDDY_BROKER_DENY / host-op`）。
  绕法：`npx tsc -p apps/usercenter/tsconfig.app.json --outDir /tmp/uc-build`，
  产物拷到 `dist/apps/usercenter/`，再建
  `dist/apps/usercenter/node_modules/@app/common -> ../../libs/common/src` 软链即可运行。
